# compassion-world-members 互換性確認

2026-08-22時点の `main` を確認しました。

## 合致している点

- `/api/v1/catalog` は外部カタログから `section === "kitchen"` を抽出し、商品ID、コード、名称、価格、売切、表示順、オプショングループを扱う
- `/api/v1/orders` とDBスキーマは `WAITING_STORE_PAYMENT / PAID / ACCEPTED / COOKING / READY / PICKED_UP / EXPIRED / CANCELLED` を定義済み
- 決済方法は `STORE / STRIPE` を定義済み
- `requestId` 由来の注文IDで、注文作成の基本的な重複防止を実装済み

## 統合前に解消が必要な差分

1. 注文作成リクエストが `productId` と数量しか受け取らず、選択した無料・有料オプションと調理指示を保存しない。
2. `order_items` に税率・税額・オプションの注文時スナップショットがなく、合計も現在の商品価格だけで算出している。
3. `orders` に提供予定時刻、注文チャネル、楽観ロック用versionがない。
4. 状態履歴、更新API、キッチン向け一覧・再接続イベントAPI、READYイベントOutboxがない。
5. `POST /orders` は店頭決済注文だけを作成し、Stripe決済確定からの注文受付経路は未実装。
6. カタログ型に営業時間、時間帯限定、税情報が露出していない。外部正本に存在する場合も共通API契約へ追加が必要。
7. `requestId` が不正または欠落するとサーバー側で新規生成されるため、通信失敗後にクライアントが同じIDを再送しない限り二重注文を防げない。注文作成ではクライアント生成の冪等キーを必須にするのが安全。

## 後方互換の方針

既存フィールドと状態名は維持します。新しい注文詳細は追加フィールドとして返し、旧クライアントが無視できる形にします。キッチン固有エンドポイントは `/api/v1/kitchen/*` として分離し、共通注文API側に実装します。このリポジトリはそのAPIの利用者に留めます。
